# App-owned UI development

Use this guidance for app-owned UI architecture, adaptation, and navigation work. Load the additional UI ownership, copy/presentation, or runtime documents routed by [AGENTS.md](../AGENTS.md) only when the affected surface crosses those concerns.

## App-owned UI, adaptation, and navigation

- Use resource-backed localized text for app-owned UI. Follow [Localization contract](localization.md) for text ownership and resolution at the presentation/output boundary; preserve MIDlet, user, and machine content according to that contract.
- Build new or materially changed app-owned presentation with Jetpack Compose Material 3 and the project theme/shared components. Keep intentional Android View, renderer, input, emulator, and Java ME API boundaries native when they still own platform or compatibility behavior.
- Preserve application behavior during incremental UI migration. Do not change Java ME API behavior merely to facilitate Compose.
- Derive layout decisions from the current container constraints, window size, and insets rather than device names or orientation alone. A compact landscape window remains compact; a portrait tablet may already have room for a larger layout.
- Select Android versions, window sizes, heights, orientations, themes, text scales, system bars, cutouts, gesture navigation, and IME states according to the platform and layout risks introduced by the change. Exercise minimum or target Android versions when version-specific behavior is material rather than as a universal matrix for every UI edit.
- Use adaptive components or multiple panes only when simultaneous content provides a concrete usability benefit. Preserve a clear single-pane fallback, readable line lengths, and stable selection when the window changes size.
- Add a navigation framework only when a flow needs independent destination history, deep links, results, or another navigation contract that existing application state does not already represent. Do not mirror pager tabs, filter/sort state, dialog visibility, or a controller-owned hierarchy into a second back stack.
- Keep one authoritative owner for navigation and selection state. When a route or selection already defines the current content, derive adaptive pane visibility from that state instead of synchronizing it with a separate navigator.
- Retain Library list/grid viewport, search, and scroll chrome outside disposable pager content, scoped to the active workdir and Collection route. Ordinary tab return uses native saved Lazy state and reveals navigation until the next content scroll; explicit metadata-editor returns may use a captured viewport or stable-item anchor. Do not replay delayed navigation anchors over a live list. Commit state-changing tab effects after the pager settles, so a reversed gesture does not clear selection. Search focus expands the header and starts results at the top; short content stays expanded. A partly scrolled header rests in place rather than snapping open, with Library title, search/sort, and quick filters independently becoming non-interactive when their touch bounds reach the system-bar inset. Quick filters belong only to the main Apps Library, not Collection members or overview; switching quick filters resets the displayed list/grid to its first result without resetting search focus, header offset, or bottom navigation visibility. Deep list/grid rows and the header travel together in either scroll direction; when the leading header placeholder enters the viewport, it takes over the consumed delta without moving rows twice. The visible header height and Lazy placeholder share one scroll-consumption contract, so filtered or short result sets never retain a full-height blank spacer beneath partially hidden controls. System Back from a focused search dismisses search focus before navigating out. Keep lazy viewports and their trailing navigation inset stable while the bottom navigation bar fades over the content; do not animate or reclaim their measured height. Compact MIDlet configuration uses the same standard Material 3 navigation bar, retaining its existing pager destinations, rail adaptation, and IME behavior. The File Picker keeps its standard Material 3 BottomAppBar for selection actions rather than representing Cancel and Choose as navigation destinations. Navigation item taps animate only adjacent pager destinations; non-adjacent taps jump directly without rendering intervening tabs, while manual swipes retain the normal pager gesture.
- Use Material 3 adaptive pane scaffolds for verified list-detail or supporting-pane behavior when they fit the supported Android range. Test compact Back behavior, selection and process restoration, and transitions between single- and multi-pane windows.
- Use `AdaptiveAlertDialog` for short Material 3 decisions and `adaptiveDialogLayout()` for custom Compose modal surfaces. Keep the shared adaptive width policy, let height wrap content, and bound only overflowing bodies with a lazy container or `verticalScroll` so titles and actions remain reachable.
- Keep `DropdownMenu` for short anchored choices. Use a custom constrained dialog or a full-screen destination for long forms; do not change presentation type merely because orientation changes. Modal scrims must cover the owning surface, hide underlying semantics, preserve Back/outside-dismiss policy, and remain usable with the IME and 200% text.
- Keep touch targets at least 48dp where practical, expose labels/state/actions to accessibility services, and avoid duplicate focus targets by putting selection/toggle semantics on the containing row while making its indicator inert.
- Keep UI work economical on low-end devices: move I/O and expensive transforms off the main thread, use lazy containers and stable keys for long data sets, remember derived work with complete keys, and avoid per-frame persistence, duplicate state, or decorative effects that trigger broad recomposition.
- Apply [Testing strategy](development.md#testing-strategy) and [Visual verification](development.md#visual-verification-and-screenshot-references) to affected UI failure modes, including Back/restore, modal overflow, dismissal, action reachability, and accessibility semantics.
- For internal app icons, prefer official Material Symbols when suitable; use a repository-provided helper when available before creating a custom icon.
