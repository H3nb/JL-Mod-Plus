# App-owned UI development

Use this guidance for app-owned UI architecture, adaptation, and navigation work. Load the additional UI ownership, copy/presentation, or runtime documents routed by [AGENTS.md](../AGENTS.md) only when the affected surface crosses those concerns.

## App-owned UI, adaptation, and navigation

- Use resource-backed localized text for app-owned UI. Follow [Localization contract](localization.md) for text ownership and resolution at the presentation/output boundary; preserve MIDlet, user, and machine content according to that contract.
- Build new or materially changed app-owned presentation with Jetpack Compose Material 3 and the project theme/shared components. Keep intentional Android View, renderer, input, emulator, and Java ME API boundaries native when they still own platform or compatibility behavior.
- Preserve application behavior during incremental UI migration. Do not change Java ME API behavior merely to facilitate Compose.
- Derive layout decisions from the current container constraints, window size, and insets rather than device names or orientation alone. A compact landscape window remains compact; a portrait tablet may already have room for a larger layout.
- Select Android versions, window sizes, heights, orientations, themes, text scales, system bars, cutouts, gesture navigation, and IME states according to the platform and layout risks introduced by the change. Exercise minimum or target Android versions when version-specific behavior is material rather than as a universal matrix for every UI edit.
- Use adaptive components or multiple panes only when simultaneous content provides a concrete usability benefit. Preserve a clear single-pane fallback, readable line lengths, and stable selection when the window changes size.
- Add a navigation framework only when a flow needs independent destination history, deep links, results, or another navigation contract that existing application state does not already represent. Do not mirror pager tabs, filter/sort state, dialog visibility, or a controller-owned hierarchy into a second back stack.
- Keep one authoritative owner for navigation and selection state. When a route or selection already defines the current content, derive adaptive pane visibility from that state instead of synchronizing it with a separate navigator.
- Preserve the Library list/grid viewport, active collection route, scope, and search/chrome state when returning from contextual settings, dialogs, Search, or metadata editing. State must belong to the applicable workdir and collection identity; a scope change must not expose another workdir's data. Returning to a Library context must not produce a flash or a delayed viewport jump over active user input.
- Library title, scope/sort controls, quick filters, and application rows scroll as one coherent surface in both directions. Partial scroll positions must not leave large blank gaps or cause rows to jump when header controls enter or leave view; short results expand their visible controls rather than reserving hidden-header space. Controls obscured by system bars must not accept touches. At large font sizes the brand wordmark and Search/Settings actions must remain readable and reachable.
- Keep quick filters in the All-applications scope of the Library; collection membership browsing does not inherit a hidden quick view. Switching quick views starts the new result list/grid at the top while retaining the current chrome position. A selected quick filter can be tapped again to clear it; the scope selector also offers All. Search opens as a separate expanded task surface with its own query and results and must never change the underlying Library filter. Back first dismisses its IME/focus and then closes Search without resetting the Browse viewport.
- Preserve collection selection, membership editing, workdir-scoped collection identity, contextual Back, and controller accessibility. The Library has a single root, reached through its header's scope selector and Search/Settings actions. A horizontal content gesture cannot switch root destinations or trigger unrelated actions. Selecting a collection opens its existing detail/management flow; returning restores the prior Browse viewport.
- Hierarchical child pages use short directional motion and Back reverses its direction. Config still owns its separate sibling-tab behavior, described below. Search expansion, modal dialogs and data/loading state changes retain distinct presentation semantics and must not delay the primary application launch interaction.
- For Config hierarchical subpages, keep transitions short and directional and derive their identity from existing page state. Opening and Back use opposing motion; only the active page receives input and accessibility focus. Bar/rail navigation selects any tab directly without displaying intervening pages; finger-driven pager swipes continue to follow gestures. No secondary navigation stack is needed.
- Full-screen Library About and Updates overlays use the same short entry/return direction. Keep the underlying Library inaccessible until their exit animations finish; do not add a second route history or animate the metadata editor without preserving its viewport/IME restoration contract.
- Internal full-screen Activities (global Settings, Profiles, MIDlet Config, Control Skin, Key Mapper, diagnostic list/detail, and app-owned File Picker) use the same 220 ms small horizontal slide and 180 ms fade on entry and the reverse exit. Scope the Android window motion to those page themes; do not apply it to the launcher, guest runtime, or translucent Memory Editor. File selection still preserves its own navigation and cancellation semantics. Android 14+ configures activity open/close transitions on the destination to keep predictive Back's commit phase coherent; older platforms use the scoped window animation style.
- Control Skin gallery/editor/inline-detail navigation uses short, paired transitions derived from its existing selection state; preview bitmaps stay available until the outgoing editor finishes and are then released. Its normal detail sheet retains Material motion. Memory Editor tabs use the same short directional motion rather than a second pager, preserving list positions and the outgoing Inspector snapshot while Back changes the active tab. Busy installer states and File Picker folder contents remain data-driven rather than being treated as navigation pages.
- At the Config root, Android owns system Back so predictive cross-Activity navigation can run; internal subpages and profile drafts continue to intercept Back to preserve their behavior.
- The single-root Library has no permanent bottom navigation bar or rail; compact MIDlet Config still uses its applicable Material 3 navigation bar. File Picker Cancel/Choose remain selection actions, not destinations. Implementations may change state-saving, spacer/scroll accounting, animation, or component structure as long as observable contracts, ownership, and performance requirements remain intact.
- Use Material 3 adaptive pane scaffolds for verified list-detail or supporting-pane behavior when they fit the supported Android range. Test compact Back behavior, selection and process restoration, and transitions between single- and multi-pane windows.
- Use `AdaptiveAlertDialog` for short Material 3 decisions and `adaptiveDialogLayout()` for custom Compose modal surfaces. Keep the shared adaptive width policy, let height wrap content, and bound only overflowing bodies with a lazy container or `verticalScroll` so titles and actions remain reachable.
- Keep `DropdownMenu` for short anchored choices. Use a custom constrained dialog or a full-screen destination for long forms; do not change presentation type merely because orientation changes. Modal scrims must cover the owning surface, hide underlying semantics, preserve Back/outside-dismiss policy, and remain usable with the IME and 200% text.
- Keep touch targets at least 48dp where practical, expose labels/state/actions to accessibility services, and avoid duplicate focus targets by putting selection/toggle semantics on the containing row while making its indicator inert.
- Keep UI work economical on low-end devices: move I/O and expensive transforms off the main thread, use lazy containers and stable keys for long data sets, remember derived work with complete keys, and avoid per-frame persistence, duplicate state, or decorative effects that trigger broad recomposition.
- Apply [Testing strategy](development.md#testing-strategy) and [Visual verification](development.md#visual-verification-and-screenshot-references) to affected UI failure modes, including Back/restore, modal overflow, dismissal, action reachability, and accessibility semantics.
- For internal app icons, prefer official Material Symbols when suitable; use a repository-provided helper when available before creating a custom icon.
